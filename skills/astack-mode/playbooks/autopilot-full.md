### Autopilot-full

**You own the verdicts, never the PRs. One owner carries each PR from build to merge, and nothing merges until your swarm, which never wrote the code, has proven the code that lands.**

A verdict covers one patch and green CI covers one head. Step 4 runs a full swarm once, and again only for a major change. The patch-id rule in `playbooks/shipping.md` can carry a lane's result, and every new head needs its own green CI.

1. **The operator's gates come first.** The grant covers only the queue's items, so items the operator names as theirs and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
2. **Spawn one owner per PR, and keep its work where a replacement can find it.** Resolve the forge once for the program (`gh` CLI and/or `github-mcp-server`). Each owner runs via `invoke_subagent` (`TypeName: "self"`, `Workspace: "branch"`) or as a named worker on a native `/swarm` board (`swarm{action: "add", workspace: "branch"}`). Each owner builds, opens its PR per `playbooks/opening-a-pr.md`, proves the change on the real artifact, babysits to green per `playbooks/babysit.md`, and merges once steps 4 and 5 clear it.

   Open the PR early so CI and bots run alongside the work. The code is ready only after `/deslop` (`skills/deslop/SKILL.md`) and `/no-comments` (`skills/no-comments/SKILL.md`), so verification runs on finished code. Then rebase onto current trunk and report the code-ready head before self-proof, so verification runs on the base the patch lands on. Report every later head, and merge-ready once self-proof, CI, and babysit are done. Fix rounds stay on that base unless trunk conflicts, breaks CI, or lands a known concurrent change to the same files, because each rebase restarts CI. Run the repo's checks for the touched paths on the committed head before the code-ready push and before a later push that needs a verifier.

   Assume a session can restart at any time. Soon after starting, push and maintain a decision trail (`skills/show-me-your-work/SKILL.md`), then push each finished unit before starting the next. Record each spawned worker/subagent id and state so replacements recover cleanly. Never call `swarm{action: "kill"}` on an author worker before its commits are pushed/merged. Force-push only your own branch, with `--force-with-lease` pinned to the SHA you last pushed or took over; stop and report to the coordinator on any unexpected external push.
3. **Run owners in parallel off trunk, never stacked,** so each PR lands on its own.
4. **Swarm-verify once.** A full verification swarm runs once, at the code-ready head. Another full swarm runs only for new behavior, a redesign, or a large new diff. A rebase, a merge-conflict resolution, or a minor fix gets a single `@verifier` at the new head, and a wording-only change gets none. Coordinate independent `@verifier` workers via native `/swarm` (`workspace: "inherit"`) or `fanout` (`skills/fanout/SKILL.md`) at the code-ready SHA. They re-run the gates, prove the load-bearing behavior live on the real surface through AStack's `control-ui` or `control-cli` (or the repo's `verify-<app>` driver), and audit the diff. The verdict is not clean without the live lane, or before you audit the merge-ready report's `#seq` receipts.

   Block a PR only for a problem you can show, with a failing run at the head or a doc line the PR made wrong. A problem the PR's base already has, whether trunk or the PR below it in a stack, doesn't block unless the PR copies it or newly reaches it. Only a bug a user would hit, a failed gate, or a wrong shipped doc blocks, and everything else goes in a follow-up.
5. **The owner merges only what you verified, tested on the trunk it lands on.** Green CI alone never authorizes a merge. Once the swarm's lanes have started, merge prep rebases onto current trunk, reports the new head, and waits for green CI.

   Right before merging, fetch trunk and ask whether its changes can affect the patch, because rebasing for every trunk move never ends. Rebase and wait for CI when the code that would land was never tested, as with a conflict, a file both sides changed, or a change to which checks run for the PR. A lockfile both sides changed needs no rebase when a frozen install passes on the merge result and the packages the PR changes resolve there as on the head, because that install tests the lockfile that would land, and a failing install means the rebase must repair it. When trunk changed a caller of the patch or something the patch depends on, such as code it calls or a dependency version, run the patch's checks on the merge result and merge on a pass. Otherwise merge. If trunk would force a third rebase past merge prep, hold and report to the root, which sequences the colliding work.
6. **Run the coordinator layer.** Anything that loosens a gate, such as a raised budget or an allowlist entry, needs a verifier's proof and then your fresh countersign, because the owner is the one who wants green. Under a grant that covers approvals, that countersign is the approval, and the owner's record of it points at your countersign for a lane to check. A disabled or soft-failed check always comes out, because it stops guarding every case. Never give or bypass an approval the forge enforces, because no countersign covers it.

   On the operator's go, run under `/goal` with a `@monitor` swarm worker (`swarm_monitor`) and/or a recurring `schedule` (`CronExpression: "0 * * * *"`) until no delegated work remains. Each tick re-reads this playbook from trunk, reconciles unreported heads or unrecorded workers, and checks side effects (pushes, PR activity, trail rows). Replace any stalled worker cleanly. A tick that changed something ends with [`ketchup`](../../ketchup/SKILL.md); one that changed nothing stays quiet.
7. **Stand down at once on the operator's stop.** A hold reaches every owner as a zero-writes order. Each reports where it stands and keeps its brief until the operator releases it.

**Reply:** catch the operator up per the **ketchup** skill, covering each PR's state and verdict, what merged, countersigns and why, open operator gates, and parked follow-ups, with links to each PR and the trails. When native `/swarm` ran, post `[done] <summary>` (no `@`) once the run clears and end the reply with the exact `open_board` value from `swarm{action: "status"}` on its own line (note **Overview > Subagents** or CLI `/agents` when subagent owners ran).
